# Надёжность SBM и проверка нагрузки

Состояние на 25 октября 2026 года. Изменения относятся ко всем 11 старым адаптерам и общему NeoForge 26.1/26.2/26.3 JAR. Старые JVM используют JNA, Java 25 использует Panama. Linux по-прежнему требует runtime своей группы Java. Выделенные серверы остаются вне этого этапа.

UUID Minecraft сохраняется без изменений. Привязка к SteamID и новый режим смены UUID исключены из текущего плана по согласованию с владельцем. SteamID продолжает использоваться для доступа, банов и владения игровой/голосовой сессией.

## Исправления

Пустой receive batch больше не считается работой. Обрабатываются оба варианта backend: null и пустой массив. Конец входящей очереди при закрытии peer также распознаётся сразу, вместо ожидания двухсекундного deadline. Пустой массив Panama переиспользуется.

При активных соединениях без сообщений пауза приёма растёт 1 → 2 → 4 мс. Полученные данные сбрасывают backoff. Без соединений остаётся ожидание condition. Реальный выигрыш CPU и влияние на задержку ещё не измерены.

Ошибки чтения одного native batch закрывают затронутый мост, не обрывая обработку остальных соединений. Ошибка голосового receive очищает соответствующий локальный socket/relay. Отложенная очистка старой голосовой сессии не закрывает новую.

JNA и Panama отвергают некорректные count/payload и повторный pointer. При ошибке выполняется cleanup оставшихся сообщений, каждый pointer освобождается один раз. Ошибка Release сохраняется рядом с исходной причиной. В FFM для отслеживания адресов используется примитивный массив вместо HashSet с boxed Long. Отправка прямого непрерывного ByteBuf в Panama больше не создаёт пустую Arena; heap/composite buffer сохраняет ограниченное копирование.

## Управление очередью

Общая TransportPolicy задаёт одинаковые параметры обоим backend:

| Параметр | Значение |
| --- | --- |
| Steam native send buffer | 2 MiB |
| Steam send-rate ceiling | 8 MiB/s |
| Максимальное окно pending reliable | 256 KiB на мост |
| Предельное оценочное время уже накопленной очереди | 250 мс |
| Повторная выборка telemetry | Не чаще раза в 5 мс на мост |
| Максимальная часть одной отправки | 32 KiB |
| Работа одного прохода отправки | До 256 KiB |

Окно адаптируется к текущему send rate Steam: примерно 100 мс данных, с границами 4–256 KiB. На медленном соединении уменьшается и длина следующей отправки. Новые bytes, уже переданные Steam после последнего snapshot, учитываются до следующей выборки. Успешный Send не означает, что пакет уже пришёл игроку.

Когда окно заполнено, приостанавливается чтение локального TCP этого моста. Его данные остаются в ограниченной Java-очереди. Остальные мосты продолжают работу. Если telemetry недоступна, отправка опирается на результат Steam, включая LimitExceeded. Постоянно заполненная очередь имеет прежний timeout 30 секунд.

250 мс являются порогом управления очередью, а не гарантией сетевой задержки. Внешний канал, Relay, Wi-Fi, JVM и тики Minecraft могут добавлять собственное ожидание. Отправитель не переставляет Minecraft-пакеты местами ради приоритета чата.

По-прежнему действуют пределы payload: 8 MiB на каждое направление моста и 128 MiB суммарно для игровых мостов процесса. Это не предел всей памяти Minecraft: сюда не входят все ёмкости Netty, native Steam buffers и игровой мир. Нового ограничения числа участников не добавлено; лимиты самого Minecraft сохраняются.

## Диагностика

В окне управления хостом у игрока появилась вторая строка:

`Steam: 24 KiB / 80 ms`

Это текущий объём ожидающих отправки bytes и оценка времени очереди Steam. Значения обновляются вместе со snapshot списка, примерно раз в секунду. Знак вопроса означает отсутствие пригодных текущих метрик.

Кнопка «Диагностика» сохраняет `logs/steambridge-diagnostics.txt` в папке игрового экземпляра. Повторный экспорт заменяет файл через временный файл. Отчёт содержит:

- JVM, ОС и состояние runtime/клиента.
- Маршрут direct/Relay, RTT и доступность метрик.
- Очереди Steam и локального TCP, число повторных отправок.
- Пиковые очереди и время native-очереди.
- Категорию последнего закрытия моста.

SteamID, имена игроков, адреса и auth tickets в этот отчёт не записываются. Полная исходная причина Minecraft и stack trace по-прежнему находятся в latest.log. Закрытие моста также пишет summary в лог. Кнопка находится в управлении хостом; для диагностики гостя сохраняйте его latest.log.

## Что проверяется автоматически

Матрица Java 8/17/21 использует реальные соответствующие версии JNA и Netty: по 101 тесту на каждой JVM. Java 25 отдельно выполняет 112 общих и FFM-проверок. Всего 415 выполнений без ошибок и пропусков.

Проверки транспорта используют настоящие локальные TCP-сокеты и один общий Netty event loop:

1. Тридцать два моста передают разные последовательности bytes. У первого native-очередь заполнена, остальные 31 завершают передачу. Затем первый продолжает и сохраняет порядок данных.
2. Восемь мостов, остановленный клиент отменяется: остальные данные сохраняются, его ByteBuf и общий memory budget освобождаются.
3. Пять мостов: один получает LimitExceeded, остальные четыре продолжают передачу.

Это моделирование Steam-ответов с настоящим локальным TCP. Здесь нет 32 Steam-аккаунтов, NAT, настоящего Relay или 32 Minecraft-клиентов. Оно проверяет изоляцию очередей и целостность bytes, а не доказывает игровую ёмкость.

Отдельные тесты проверяют 64 независимых окна отправки, недоступную/stale telemetry, адаптацию медленного маршрута, null/empty batch, graceful drain, duplicate pointers, cleanup после ошибок, конфигурационную политику обоих backend и сохранение диагностического файла. FFM-стенд использует настоящие downcall/upcall с подставленными ответами, не вызывает SteamAPI_Init.

Отчёты итогового прогона: build/20261025-reliability-results.json, build/20261025-reliability-build.log, build/test-reports/results.json, build/panama-test-results.json. Объём ABI и исходное ограничение проверки ZIP Valve сохраняются.

## Один ручной тест нагрузки

Сначала убедитесь, что все игроки используют соответствующие одной сборке SBM, совместимые версии Minecraft и одинаковый модпак. Для проверки третьего участника нужны хотя бы три участника вместе с хостом; для сравнения двух удалённых маршрутов предпочтительны хост и три гостя.

1. После входа всех игроков открыть управление хостом и сохранить диагностику. Несколько минут проверить обычный чат, движение и голос.
2. Один гость быстро перемещается и загружает новые чанки. Другой остаётся рядом с хостом, пишет сообщения и разговаривает. Проверить, не появляются ли у него новые задержки или отключения.
3. Повторить, сменив гостя, который загружает чанки. Так выявляется зависимость от конкретного маршрута.
4. При наличии естественно медленного гостя повторить с ним. Искусственно ухудшать сеть для первого прогона не требуется.
5. Во время заметного зависания сохранить диагностику, записать время и собрать latest.log хоста и затронутых гостей.
6. Один гость выходит и входит повторно, пока остальные играют. Затем проверить смену мира и повторное открытие Steam-host.

Смотреть нужно не на одну цифру ping: важны рост очереди, ожидание, сохранение связи у остальных и исходная причина закрытия. Нулевая Steam-очередь не исключает лаги TPS, GC или самого модпака. Стабильное поведение этого сценария полезно, но точные p95, throughput и память требуют отдельного измерения.

Реальные Steam direct/Relay, обе стороны Windows/Linux, voice-моды, применение mixins и GUI каждой Minecraft-интеграции остаются обязательными игровыми проверками. Нельзя обещать отсутствие ошибок для трёх и более игроков только по unit-тестам.
